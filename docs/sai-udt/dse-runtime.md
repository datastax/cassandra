# HCD-653: DSE Search 6.9.26 runtime behaviour for UDT and tuple fields

One local DSE 6.9.26 node started with Search (`dse cassandra -s`), default settings, schemas generated by
`CREATE SEARCH INDEX ON <table>` with no options unless noted. Source-level answers come separately
(issue #105). This file is the behavioural reference for the SAI compatibility tests.

## Test schema
```
CREATE TYPE geo (lat double, lon double);
CREATE TYPE address (street text, city text, zip int, loc frozen<geo>, tags set<text>);
CREATE TYPE person (name text, age int, home frozen<address>);
u_frozen    (id int PK, addr frozen<address>)
u_nonfrozen (id int PK, p person)                  -- non-frozen UDT, scalar + frozen fields
u_nested    (id int PK, p frozen<person>)
t_tuple     (id int PK, t tuple<text,int,double>)
u_list      (id int PK, addrs list<frozen<address>>)
u_set       (id int PK, addrs set<frozen<address>>)
u_map       (id int PK, addrs map<text, frozen<address>>)
t_list      (id int PK, ts list<frozen<tuple<text,int>>>)
```

## Index creation
| shape | `CREATE SEARCH INDEX` (defaults) |
|---|---|
| frozen UDT, nested frozen UDT, non-frozen UDT | accepted |
| tuple | accepted |
| `list<frozen<udt>>`, `set<frozen<udt>>`, `list<frozen<tuple>>` | accepted |
| `map<text, frozen<udt>>` | rejected: "The search index schema could not be auto-generated because: Dynamic fields cannot be tuple/UDT on CQL3 tables, offending field: addrs*" |
| adding a map-of-UDT field by hand (`ALTER SEARCH INDEX SCHEMA ... ADD ... @type='TupleField'` on an index that did not generate the type) | rejected: "Unknown fieldType 'TupleField'" |

## Generated schema
- The column itself gets type `com.datastax.bdp.search.solr.core.types.TupleField`; every leaf gets a field
  named by its **dotted path**, recursively: `p.home.loc.lat`. Nested UDTs get their own `TupleField`
  (`p.home`, `p.home.loc`).
- Tuple components are named `field1`, `field2`, ... (`t.field1`).
- Leaf types follow the plain-column mapping (text → StrField, int → TrieIntField with docValues,
  double → TrieDoubleField with docValues); a `set<text>` inside a UDT becomes a multiValued StrField.
- For collections of UDTs/tuples the column field is `multiValued="true"`, the leaves are single valued:
  each element is a **child document** (Lucene block join; a bad query reports
  "child query must only match non-parent docs, but parent docID=… matched childScorer=…").
- `CREATE SEARCH INDEX ... WITH COLUMNS id, p.age` indexes only that UDT field (`p` TupleField + `p.age`).

## Queries (`solr_query`)
Data: u_list row 1 = [{Rome, 200, lat 1}, {Milan, 100, lat 3}], row 2 = [{Rome, 100, lat 5}];
u_frozen 1 = {a, Rome, 200, lat 1}, 2 = {b, Paris, 100, no loc}; u_nonfrozen 1 = {Ann, 30, home Rome},
2 = {Bob, 40} then `UPDATE SET p.age = 41`; t_tuple 1 = (foo,1,1.5), 2 = (bar,2,2.5); t_list 1 = [(foo,1),(bar,2)].

| query | result | meaning |
|---|---|---|
| `addr.city:Rome` (no parser) | none | UDT leaves are only reachable through the tuple parser |
| `{!tuple}addr.city:Rome` | 1 | field match on frozen UDT |
| `{!tuple}addr.loc.lat:1.0` | 1 | nested field |
| `{!tuple}addr.street:b*` | 2 | prefix/wildcard |
| `{!tuple}addr.city:rome` | none | StrField: exact, case-sensitive |
| `{!tuple}addr.city:[P TO S]` | 1, 2 | string range |
| `{!tuple}addr.city:*` / `{!tuple}addr.loc.lat:*` | 1, 2 / 1 | field exists (not null) |
| `{!tuple}p.age:41` (non-frozen, after single-field UPDATE) | 2 | single-field updates are reindexed |
| `{!tuple}p.home.city:Rome` | 1 | frozen UDT inside non-frozen UDT |
| `{!tuple}t.field1:foo`, `{!tuple}t.field2:[2 TO *]` | 1 / 2 | tuple components, numeric range |
| `{!tuple}addrs.city:Rome` | 1, 2 | any element matches |
| `{!tuple}addrs.city:Rome AND addrs.zip:100` | **2** | **AND inside one tuple query = same element** |
| `{!tuple}ts.field1:foo AND ts.field2:2` / `... AND ts.field2:1` | none / 1 | same for list of tuples |
| `{!tuple}addrs.city:Rome OR addrs.city:Milan` | 1, 2 | OR within the element |
| `{!tuple}addrs.city:Rome AND NOT addrs.zip:100` | 1 | negation within the element |
| `{!tuple}addrs.zip:[150 TO *]`, `{!tuple}addrs.loc.lat:[2 TO 6]`, `{!tuple}addrs.tags:y` | 1 / 1, 2 / 1, 2 | ranges, nested field in element, set inside element |
| `{"q":"{!tuple}addrs.city:Rome","fq":"{!tuple}addrs.zip:100"}` | 1, 2 | separate q/fq = independent elements (any element each) |
| `id:1 AND {!tuple}addrs.city:Rome` | 1 | tuple query combined with a plain field |
| `{!tuple}addrs.zip:200 AND addrs.loc.lat:1.0` | none | mixing nesting levels in one tuple query does not match (row 1 has that element) |
| `{!tuple}a AND {!tuple}b`, `{!tuple}a AND _query_:"{!tuple}b"` | none | second parser inside a tuple query is not honoured |
| `{!tuple}*:* AND NOT addr.loc.lat:*` | server error (block join child/parent) | "is null" on a nested field is not expressible |
| sort on `addrs.zip` / `addr.zip` | error "Sorting on Tuple fields is not supported. Offending field [<f>]" | |
| facet on `addr.city` | error "Faceting on Tuple fields is not supported. Offending field [<f>]" | |

## CQL `WHERE` on UDT fields
`SELECT ... WHERE addr.city = 'Rome'` and `WHERE p.age = 41` fail with `SyntaxException ... no viable alternative
at input '.'` even with a search index: DSE has no CQL predicate on UDT fields; everything goes through
`solr_query` + `{!tuple}`.

## Use cases SAI must cover (from the above)
1. Equality / range / prefix(LIKE) / not-null on a leaf of a frozen UDT, nested frozen UDT, tuple component.
2. Same on a non-frozen UDT, with single-field updates.
3. Collections (list/set) of frozen UDTs or tuples: "any element matches" and **"several conditions on the
   same element"** (with OR and NOT inside the element).
4. Selecting which fields are indexed (`WITH COLUMNS p.age`).
5. Not required (DSE rejects): maps of UDTs, sort/facet on UDT fields, cross-level same-element conditions.
